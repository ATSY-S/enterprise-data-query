# 企业级评估与优化方向

评估时间：2026-11-21
对照对象：JimuChatBI / SuperSonic / DB-GPT，以及字节等公司的后端工程规范

---

## 一、三次回滚够不够？

**结论：三次重试作为"自动纠错"是够的；作为"企业成品"不是靠增加重试次数解决的。**

企业系统的可靠性来自三件事，而不是无限重试：

| 维度 | 现在的实现 | 企业做法 | 要不要做 |
|---|---|---|---|
| 错误分类 | 所有错误一视同仁，都回灌重试 | 语法错误自动重试；权限/安全错误立即拒绝；语义歧义反问用户 | **做**：避免对不可恢复错误白试 3 次 |
| 结果可控 | 生成什么就执行什么 | 支持"预览 SQL，用户确认后执行" | **做**：这是企业 BI 的标配（Human-in-the-loop） |
| 失败兜底 | 失败就返回错误 | 失败后给用户的不是报错，而是"哪里错了 + 建议怎么问" | **做**：体验差别最大的一点 |
| 重试次数 | 固定 3 次 | 按错误类型动态：语法错 2 次、字段错 3 次；总耗时上限 10 秒 | 做：配置化即可 |
| 反馈闭环 | 没记录用户满不满意 | "有用/无用"反馈 → badcase 库 → 优化提示词 | 论文可写，先留接口 |
| 缓存 | 无 | 高频问题缓存结果，降低延迟和成本 | 暂不做，毕设范围内意义不大 |

**重试次数本身不要再加大**：实测 30 道题 0 次重试，说明模型在限定范围内很稳；盲目加到 5 次只会让失败请求更慢，不会提高成功率。

## 二、后端结构与工程规范评估

按互联网公司（字节/腾讯）后端 Code Review 的常见标准看现在的代码：

| 项目 | 现状 | 评价 |
|---|---|---|
| 分层 | 单文件 agent.py 包办 LLM、纠错、统计、图表、导出 | 不理想：应拆 service / repository / schema |
| 配置 | config.py 集中管理，环境变量外置 | 基本合格 |
| 安全 | 正则守卫拦写操作 | 不够：正则是黑名单，应有白名单 + 参数化视图 |
| 错误处理 | try/except 返回 dict | 不理想：应定义业务异常 + 统一响应结构 |
| 日志 | 无结构化日志 | 不合格：企业排查问题必须要 |
| 类型 | 无类型注解、无 Pydantic schema | 不合格：接口契约不清 |
| 测试 | 只有评测脚本，没有单元测试 | 不合格：CI 跑不起来 |
| 可观测性 | 无 trace_id / 耗时分解 | 不合格 |

**但要注意**：这是本科毕设，不是生产系统。全按大厂规范改会把你拖进工程泥潭，论文写不完。我的建议是**只做"答辩能加分、工作量可控"的四项**：

1. 错误分类重试（对应上面的表）
2. 用户确认模式（SQL 预览接口）
3. 结构化日志 + 统一响应格式
4. 类型注解 + Pydantic schema

分层重构（拆 6 个文件）和单元测试先不做——投入产出比低。

## 三、前端评估

**适配问题**：原版确实有 bug——全局没有一条 `@media`，侧栏固定 232px、统计卡固定四列，手机和小屏会挤坏。已修复：

- ≤1024px：侧栏收窄为 72px 图标栏，统计卡两列
- ≤640px：侧栏变底部导航栏，统计卡两列，输入框与按钮换行，聊天区高度重算
- 功能网格从固定三列改为响应式

**参考材料调研**：

- `vue-vben-admin`（vbenjs，33.8k stars，最新提交 2026-11-19）：Vue3 + TS + Vite + Monorepo + Tailwind v4，工程化强，表格/表单/权限路由齐全。**适合参考架构，不适合直接搬**——毕设引入 Monorepo 会把重心从"查询系统"变成"学框架"，答辩讲不清。
- `vue-element-admin`：链接已失效（404）。
- 结论：保持现在的 Vue3 + Element Plus 轻量结构，只借鉴 vben 的"侧栏 + 标签页 + 统一请求封装"思路。

**下一步可选优化**（按性价比排序）：

1. 对话页加"执行步骤"折叠面板（展示生成 SQL → 执行 → 重试的链路）——用户能看到 Agent 在干什么，很像企业产品
2. 结果表格加排序/分页/列筛选（现在只显示前 20 行）
3. 图表从后端 PNG 换成 ECharts 交互图（工作量大，暂缓）
4. 加"反馈"按钮（有用/无用），为论文里的人机协同闭环提供数据
